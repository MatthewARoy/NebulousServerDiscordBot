## Rollout sequence

Reserve roughly 45–60 minutes for the supervised rollout and initial observation,
excluding any time needed to repair a failed preflight. Expect brief interruptions
at container replacement; startup time on the small VM is variable.

1. **Approve and freeze.** Close the gates above; obtain production go/no-go.
   Review/merge the PR, including the built-in guide. Verify the chosen image and source
   revision. Merge alone does not deploy. If main advances, reconcile the change
   and reassess the candidate before using the old artifact.
2. **Protect production.** Record the current image, running configuration and
   resource baseline. Retain the exact 2.9.1 image and private copies of Compose
   and environment files. Take a consistent SQLite online backup, verify integrity,
   and restore/open a temporary copy without starting a second production bot.
   Check expected tables and row counts. Verify disk/RAM headroom before loading
   the image. No schema changes are introduced by this release.
3. **Deploy compatibility mode.** Load the verified artifact without rebuilding
   it on the small production VM. Preserve the real mounts, ports and settings;
   explicitly keep Message Content enabled for this stage. Recreate the container.
   Check version, HTTP health, gateway connection, monitoring, recent game history,
   existing status posts and prefix/mention commands. Stop here on any failure.
4. **Register production slash commands.** Snapshot the existing global tree;
   deliberately sync and verify all 19 top-level entries and advice subcommands.
   Test the production bot in the owner's test server. Confirm these are the
   global registrations, not test-guild copies masking a missing global command.
   Check the app's command availability and channel permissions in a representative
   target server with an authorized tester. Do not cut over while commands are absent.
5. **Switch off Message Content.** Set `DISCORD_MESSAGE_CONTENT=false` and recreate
   the container; a restart alone does not reload environment values. Verify
   gateway/monitoring/slash/mention/DM behavior, then disable the Portal toggle.
   Force a fresh process start to prove a new identification succeeds with all
   privileged intents off, not merely a resumed gateway session.
6. **Observe and confirm.** Run production `/listservers`, `/openlobbies`, `/stats`,
   `/graph` and a modest `/formation` in the approved test channel. Observe at least
   20 minutes after final restart: edits beyond 15 minutes, advancing monitoring
   timestamps, stable memory, no OOM/restart loop, no sustained swap thrashing,
   and no unexplained gateway or command errors. Confirm existing guild settings,
   statistics and advice remain intact. Diagnose before announcing completion.
7. **Send only approved communications.** Verify `/guide` works. Post the approved
   final notice once in each approved channel and record message IDs. Users must
   run `/nextgame` again after the last restart: its queue is in memory. No automatic
   startup broadcast or unapproved ping, DM, pin or crosspost is part of this release.

Steps 3–6 include live production tests that cannot be completed before deployment.
Keep functional command checks in the owner's test server. The previous
production approval question remains unanswered; this planning request does
not authorize production deployment.

## Stop and rollback rules

- Before the intent-off switch, a failed runtime check means restore the retained
  image and configuration while Message Content access still exists. Recheck health
  and monitoring. Restore the previous global command snapshot if registration
  must be undone; do not leave advertised commands backed by an incompatible bot.
- After intent-off, **2.9.1 is not a valid rollback**: it always requests Message
  Content. While permission still exists, compatibility mode is a temporary option;
  once access is revoked, repair forward or deploy another tested intent-off image.
- Do not restore the database simply because the application failed. There is no
  new schema migration; unnecessary restore would discard fresh statistics/advice.
  Restore only for an actual data problem, with a separate decision about data loss.
- A failed announcement does not justify reverting working bot software. Inspect
  the destination before retrying and resume only unsent, approved messages.
